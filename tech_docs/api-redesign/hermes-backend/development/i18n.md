# Internationalization (i18n) — Hermes Backend

**Project**: hermes-backend  
**Status**: Architecture Design  
**Target Languages**: English (en) — primary, Spanish (es), Portuguese (pt-BR)

---

## 1. Overview

The Hermes Backend operates in **field conditions** — remote regions of Latin America where operators and users primarily speak Spanish or Portuguese. The system interface (Web UI, API error messages, notifications, audit logs) must be accessible in the operator's native language.

### Scope of Internationalization

| What IS internationalized | What is NOT internationalized |
|---------------------------|-------------------------------|
| API error messages (RFC 7807) | User-generated message content |
| Schema validation responses | Callsigns (universal identifiers) |
| WebSocket: system events and notifications | Radio telemetry (numeric data) |
| Audit logs (`audit_logs.message`) | Radio commands (technical protocol) |
| Setup wizard (`POST /setup`) | Conversation types (`direct`, `group`, `broadcast`) |
| Emails/SMTP (message_envelopes) | RBAC roles (`admin`, `operator`, `user`, `readonly`) |
| System messages (health, clock) | Database column names |

### Supported Languages

| Code | Language | Coverage | Priority |
|------|----------|----------|:---:|
| `en` | English | 100% (default language, universal fallback) | P0 |
| `es` | Español | 100% (Latin America — Mexico, Colombia, Peru, etc.) | P0 |
| `pt-BR` | Português (Brasil) | 100% (Brazil) | P1 |

> **Note on amateur radio**: Radio terminology (frequency, mode, PTT, SWR, SNR) is kept in English per international ham radio convention. These technical terms are universal and must not be translated — radio operators in any country recognize them.

## 3. Language Detection

### 3.1 Resolution Chain

Language detection follows this priority order:

```
1. User preference (users.locale in database)
   └─ Queried once per session, cached in JWT ('locale' claim)
2. HTTP Accept-Language header
   └─ Example: "es-MX,es;q=0.9,en;q=0.8" → resolves to "es"
3. Universal fallback: "en"
```

### 3.2 Storing the Preference

The user's language preference is persisted in the database:

```sql
ALTER TABLE users ADD COLUMN locale TEXT NOT NULL DEFAULT 'en';
-- Valid values: 'en', 'es', 'pt-BR'
```

And embedded in the JWT payload to avoid repeated database queries:

```typescript
// JWT payload
interface JwtPayload {
  sub: string        // userId
  callsign: string
  role: string       // 'admin' | 'operator' | 'user' | 'readonly'
  locale: string     // 'en' | 'es' | 'pt-BR'
  sessionId: string
  iat: number
  exp: number
}
```

### 3.3 User Language Configuration

The `PATCH /users/me` endpoint accepts a `locale` field:

```json
// PATCH /api/v1/users/me — Request
{
  "locale": "es"
}

// PATCH /api/v1/users/me — Response 200
{
  "id": "uuid",
  "callsign": "XA1ABC",
  "displayName": "Base Station Alpha",
  "email": "alpha@example.com",
  "role": "operator",
  "locale": "es",
  "status": "active"
}
```

> **Note**: Changing the `locale` invalidates all existing JWT tokens for the user (old tokens carry the old locale). The client must re-authenticate via `POST /auth/login` or `POST /auth/refresh` to obtain a token with the new locale.

## 4. Impact on the REST API

### 4.1 Accept-Language Header

All API requests may include the `Accept-Language` header:

```http
GET /api/v1/conversations HTTP/1.1
Authorization: Bearer eyJhbGciOiJSUzI1NiIs...
Accept-Language: es-MX, es;q=0.9
```

### 4.2 Localized Error Responses

The `message` field and `details[].message` in RFC 7807 responses are translated according to the resolved locale:

```json
// Error 403 — user with locale=es (no explicit Accept-Language)
{
  "type": "https://hermes.example.com/errors/forbidden",
  "title": "Forbidden",
  "status": 403,
  "code": "FORBIDDEN",
  "message": "No tiene permisos suficientes para esta operación.",
  "requestId": "req-uuid"
}

// Error 400 — validation with locale=pt-BR
{
  "type": "https://hermes.example.com/errors/validation",
  "title": "Validation Error",
  "status": 400,
  "code": "INVALID_PAYLOAD",
  "message": "O corpo da requisição não atende ao esquema esperado.",
  "details": [
    {
      "field": "frequencyHz",
      "message": "Deve estar entre 1000000 e 30000000"
    }
  ],
  "requestId": "req-uuid"
}
```

> **Note**: The `title` field stays in English (RFC 7807 convention). The `code` field is a machine-readable identifier (never translated). Only `message` and `details[].message` are localized.

### 4.3 Health and System Messages

System notifications sent via WebSocket and health check responses are localized:

```json
// WebSocket SYSTEM_NOTIFICATION — locale=es
{
  "type": "SYSTEM_NOTIFICATION",
  "payload": {
    "level": "warning",
    "code": "CLOCK_UNSYNCED",
    "message": "El reloj del sistema no está sincronizado. La hora puede ser incorrecta.",
    "timestamp": "2026-07-17T12:00:00Z"
  },
  "timestamp": "2026-07-17T12:00:00Z",
  "version": 1
}
```

## 5. Impact on the Database

### 5.1 `users.locale` Column

```sql
ALTER TABLE users ADD COLUMN locale TEXT NOT NULL DEFAULT 'en'
  CHECK (locale IN ('en', 'es', 'pt-BR'));
```

### 5.2 `audit_logs.locale` Column

Audit logs record the user's locale at the time of the action, so descriptions can be reconstructed in the correct language:

```sql
ALTER TABLE audit_logs ADD COLUMN locale TEXT NOT NULL DEFAULT 'en';
```

### 5.3 `message_envelopes.locale` Column

The `message_envelopes` table (email/SMTP transport) includes the locale for email template selection:

```sql
ALTER TABLE message_envelopes ADD COLUMN locale TEXT NOT NULL DEFAULT 'en';
```

## 6. Setup Wizard (`POST /setup`)

The first-time setup wizard detects the browser's language via `Accept-Language` and presents the interface in the detected language. The admin can change the language during setup:

```json
// POST /api/v1/setup — Request (with explicit locale)
{
  "locale": "es",
  "country": "MX",
  "callsign": "XA1ABC",
  "stationName": "Estación Base Alpha",
  "radioProfile": {
    "frequencyHz": 14200000,
    "mode": "USB"
  },
  "installedApps": ["hermes-chat", "hermes-gps"],
  "adminUser": {
    "callsign": "XA1ABC",
    "displayName": "Operador de Estación",
    "password": "secure-admin-password",
    "locale": "es"
  }
}
```

If `locale` is not provided, the server detects it via the request's `Accept-Language` header. If the header is also absent, `"en"` is used.

## 7. Impact on the WebSocket Gateway

### 7.1 Authentication

The user's locale is sent in the `AUTHENTICATED` frame so the client knows which language system messages will arrive in:

```json
// Server → Client: AUTHENTICATED
{
  "type": "AUTHENTICATED",
  "payload": {
    "userId": "uuid",
    "callsign": "XA1ABC",
    "role": "operator",
    "locale": "es",
    "sessionId": "uuid",
    "serverTime": "2026-07-17T12:00:00Z"
  }
}
```

### 7.2 Localized Events

The following event types have their `message` field translated according to the user's locale:

| Event | Localized Field |
|--------|-----------------|
| `SYSTEM_NOTIFICATION` | `payload.message` |
| `CLOCK_SYNCED` | `payload.message` |
| `RADIO_STATE_CHANGE` | `payload.description` (e.g., "SWR protection activated" → "Protección SWR activada") |
| `SYNC_SUMMARY` | `payload.summary` |

### 7.3 Per-Connection Locale

Each WebSocket connection has its own locale, resolved at authentication time. Different connections from the same user may have different locales (e.g., Web UI in es, mobile device in pt-BR).

## 8. Message Content Translation

**User-generated messages are NOT automatically translated.** The content of `POST /conversations/:id/messages` is stored and transmitted exactly as sent by the sender. Automatic message translation is a future optional feature (Phase 10+).

If automatic translation is implemented in the future, the message schema would be extended as follows:

```sql
-- Future: message translations
CREATE TABLE message_translations (
  message_id TEXT NOT NULL REFERENCES messages(id) ON DELETE CASCADE,
  locale TEXT NOT NULL,  -- 'en', 'es', 'pt-BR'
  translated_content TEXT NOT NULL,
  translated_subject TEXT,
  translator TEXT NOT NULL DEFAULT 'manual', -- 'manual' | 'ai' | 'google'
  created_at TEXT NOT NULL,
  PRIMARY KEY (message_id, locale)
);
```

## 9. Email Template Translation

Emails sent via `message_envelopes` (SMTP transport for recipients with email configured) use localized HTML templates. The locale is determined by the recipient's preference (`users.locale`).

```
src/i18n/resources/en/email.json
src/i18n/resources/es/email.json
src/i18n/resources/pt-BR/email.json
```

Each file contains templates for:
- New message notification
- Password recovery
- Security alert (token reuse detected)
- System health report

## 10. Coverage Metrics and Validation

### 10.1 Coverage Verification

A build script verifies that all language files have the same keys:

```bash
npm run i18n:check
# Compares keys from en/ with es/ and pt-BR/
# Fails if any key is missing
```

### 10.2 Missing Keys

If a key does not exist in the requested locale, the system falls back to `en` and logs a warning:

```
[WARN] i18n: missing key "VALIDATION.MAX_LENGTH" for locale "pt-BR", falling back to "en"
```

## 12. Performance Considerations

| Metric | Value |
|--------|-------|
| Total resource size (3 languages) | ~60 KB |
| Load time (startup) | < 5 ms (6 JSON files via `fs.readFileSync`) |
| Runtime memory footprint | ~60 KB (JavaScript objects in memory) |
| Per-request overhead | Negligible (object key lookup + interpolation) |

Translation resources are loaded at startup and kept in memory for the entire process lifetime. The overhead is negligible for the Pi 4 (60 KB out of 4 GB RAM).
